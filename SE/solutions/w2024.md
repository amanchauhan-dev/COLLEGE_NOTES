## Q.1 (a) Why Spiral Process Model is also known as Meta Model? [03]

=> The **Spiral Process Model** is called a **Meta Model** because it combines features of many other software process models.

=> It is not a single fixed model. Each spiral cycle can use waterfall, prototyping, incremental, or other approaches depending on project risk and requirement.

### Reasons

1. **Combines multiple models**

=> It includes planning from waterfall, prototyping for risk reduction, and incremental delivery.

2. **Risk-driven model**

=> Each cycle focuses on identifying and reducing risks before development continues.

3. **Flexible framework**

=> It can be adapted for small modules, prototypes, or large system releases.

4. **Supports iteration**

=> Development proceeds through repeated spirals, and each spiral produces a better version of software.

=> Therefore, the Spiral Model is known as a meta model because it can represent and combine other process models.

## Q.1 (b) Compare Prototype Process Model with RAD Process Model. [04]

| Prototype Process Model | RAD Process Model |
|---|---|
| Used when requirements are unclear. | Used when requirements are well understood and quick delivery is needed. |
| A prototype is built to understand user needs. | Complete application is built rapidly using reusable components and tools. |
| Main focus is requirement clarification. | Main focus is fast development. |
| Customer evaluates prototype repeatedly. | Customer participates in workshops and reviews. |
| Prototype may be thrown away or evolved. | Final product is developed through time-boxed phases. |
| Suitable for new, unclear, or experimental systems. | Suitable for modular systems with tight schedule. |

### Prototype model

=> Prototype model creates a working sample of the system before full development.

=> It is useful when users cannot clearly explain requirements.

### RAD model

=> RAD stands for Rapid Application Development.

=> It uses component reuse, CASE tools, and parallel development teams for quick delivery.

=> Prototype model reduces requirement risk, while RAD reduces development time.

## Q.1 (c) Explain the working of Incremental Process Model with suitable diagram. [07]

=> **Incremental Process Model** develops software in small parts called increments.

=> Each increment delivers a working portion of the complete system. The first increment contains core functionality, and later increments add more features.

### Diagram

```text
Requirement analysis
        |
        v
+-------------------+    +-------------------+    +-------------------+
| Increment 1        |    | Increment 2        |    | Increment 3        |
| Design-Code-Test   | -> | Design-Code-Test   | -> | Design-Code-Test   |
| Core features      |    | Extra features     |    | Final features     |
+-------------------+    +-------------------+    +-------------------+
        |                        |                        |
        v                        v                        v
 Release 1                 Release 2                 Final product
```

### Working

1. **Requirement collection**

=> Overall system requirements are collected and divided into different increments.

2. **Prioritization**

=> Important and basic requirements are selected for the first increment.

3. **First increment**

=> Core product is designed, coded, tested, and delivered to the customer.

4. **Customer feedback**

=> Customer uses the first release and gives feedback.

5. **Next increments**

=> Additional features are developed and added in later increments.

6. **Final system**

=> After all increments are completed, the full software product is ready.

### Example

=> In an online shopping system:

1. Increment 1: Login, product list, search.
2. Increment 2: Cart and order placement.
3. Increment 3: Payment, tracking, reviews.

### Advantages

1. Working software is delivered early.
2. Customer feedback is received quickly.
3. Risk is reduced because core functions are tested early.
4. Easier to manage than one large release.
5. Important features can be developed first.

### Limitations

1. Requires good planning and modular design.
2. Integration between increments can become difficult.
3. Total system architecture must be planned early.

=> Incremental model is suitable when early delivery is required and requirements can be divided into modules.

## Q.2 (a) Why Software Engineering is also known as a Layered Technology? [03]

=> Software Engineering is called a **Layered Technology** because it is built on different layers that support systematic software development.

### Layers

```text
Tools
Methods
Process
Quality Focus
```

1. **Quality focus**

=> It is the foundation layer. Every software engineering activity aims to produce quality software.

2. **Process**

=> Process defines the framework for software development activities such as planning, analysis, design, coding, testing, and maintenance.

3. **Methods**

=> Methods provide technical ways to perform activities such as requirement analysis, design, testing, and estimation.

4. **Tools**

## Q.2 (b) Explain Formal Technical Review (FTR). [04]

=> **Formal Technical Review (FTR)** is a structured review activity used to find defects in software work products such as requirements, design, code, and test cases.

=> It is performed by a small group of technical people before the product moves to the next phase.

### Objectives

1. Find errors early.
2. Verify that work product satisfies requirements.
3. Check quality, consistency, and completeness.
4. Ensure standards are followed.
5. Improve team understanding.

### FTR participants

1. Review leader.
2. Author or developer.
3. Reviewers.
4. Recorder.

### FTR process

1. Planning review meeting.
2. Distributing review material.
3. Individual preparation by reviewers.
4. Review meeting and discussion.
5. Recording defects and suggestions.
6. Rework by author.
7. Follow-up by review leader.

### Benefits

1. Reduces testing cost.
2. Improves software quality.
3. Finds defects before coding or delivery.
4. Encourages technical communication.

## Q.2 (c) Define Coupling and Cohesion. Explain different types of Cohesion and its effects on software module. [07]

=> **Coupling** is the degree of dependency between two software modules.

=> **Cohesion** is the degree to which elements inside a module are related to each other.

=> Good design should have **low coupling** and **high cohesion**.

### Coupling vs Cohesion

| Coupling | Cohesion |
|---|---|
| Measures dependency between modules. | Measures relatedness inside a module. |
| Low coupling is good. | High cohesion is good. |
| High coupling makes maintenance hard. | High cohesion makes module understandable. |

### Types of Cohesion

1. **Coincidental cohesion**

=> Unrelated tasks are placed in one module.

=> It is the worst type of cohesion.

2. **Logical cohesion**

=> Related category of tasks are placed together, but selected by control flag.

=> Example: A module that handles all input operations for keyboard, file, and network.

3. **Temporal cohesion**

=> Tasks related by time are grouped together.

=> Example: Initialization module that opens files, connects database, and sets variables.

4. **Procedural cohesion**

=> Tasks are grouped because they follow a specific sequence.

=> Example: Read input, validate input, and print result.

5. **Communicational cohesion**

=> Tasks operate on the same data.

=> Example: A module that reads, updates, and prints student records.

6. **Sequential cohesion**

=> Output of one task becomes input for another task.

=> Example: Calculate marks, then calculate grade from marks.

7. **Functional cohesion**

=> All elements of a module perform one well-defined function.

=> Example: A module only for calculating salary.

=> Functional cohesion is the best type.

### Effects on software module

1. High cohesion improves readability.
2. Maintenance becomes easier.
3. Testing becomes simpler.
4. Reusability increases.
5. Low cohesion creates confusing and error-prone modules.
6. High cohesion reduces side effects during change.

## Q.2 (c) OR Illustrate Requirement Engineering with suitable diagram. [07]

=> **Requirement Engineering** is the process of discovering, analyzing, documenting, validating, and managing software requirements.

=> It helps developers understand what the customer needs and what the system must do.

### Diagram

```text

   |
   v

   |
   v
Elaboration
   |
   v

   |
   v

   |
   v

   |

```

### Activities

1. **Inception**

=> Identify stakeholders, business need, problem scope, and basic system goals.

2. **Elicitation**

=> Collect requirements using interviews, questionnaires, meetings, observation, and brainstorming.

3. **Elaboration**

=> Refine requirements using scenarios, use cases, data models, and behavior models.

4. **Negotiation**

=> Resolve conflicts between requirements and prioritize them based on cost, schedule, and value.

5. **Specification**

=> Document requirements in SRS.

=> SRS contains functional requirements, non-functional requirements, constraints, interfaces, and acceptance criteria.

6. **Validation**

=> Check requirements for correctness, completeness, consistency, feasibility, and clarity.

7. **Requirement Management**

=> Track requirement changes throughout development.

### Importance

1. Reduces misunderstanding between customer and developer.
2. Helps prepare accurate SRS.
3. Reduces rework and project failure.
4. Improves software quality.

## Q.3 (a) Explain Function and Non-functional requirements using example. [03]

=> **Functional requirements** describe what the system must do.

=> They specify services, operations, inputs, outputs, and behavior of the system.

### Examples

1. User can login using username and password.
2. System can generate monthly sales report.
3. Customer can place and cancel an order.

=> **Non-functional requirements** describe how the system should perform.

=> They specify quality attributes such as performance, security, usability, reliability, and availability.

### Examples

1. Login response must be given within 2 seconds.
2. Password must be encrypted.
3. System must be available 99% of the time.

=> Functional requirements define system functions, while non-functional requirements define quality constraints.

## Q.3 (b) Explain RMMM. [04]

=> **RMMM** stands for **Risk Mitigation, Monitoring, and Management**.

=> It is a plan used in software project risk management to handle possible project risks.

### 1. Risk Mitigation

=> Mitigation means taking preventive actions to reduce risk probability or impact.

=> Example: If new technology is risky, create a prototype before full development.

### 2. Risk Monitoring

=> Monitoring means continuously tracking risk indicators during the project.

=> Example: Track schedule delay, defect rate, staff availability, and change requests.

### 3. Risk Management

=> Management means applying contingency plans when a risk becomes a real problem.

=> Example: If a team member leaves, assign backup member and update schedule.

### RMMM plan contains

1. Risk description.
2. Probability and impact.
3. Mitigation action.
4. Monitoring indicators.
5. Contingency plan.
6. Responsible person.

=> RMMM reduces uncertainty and helps the project manager control project failure.

## Q.3 (c) OR Explain three golden rules for User Interface Design. [07]

=> User Interface Design aims to create screens that are easy to learn, easy to use, consistent, and error-free.

=> The three golden rules of UI design are suggested by Theo Mandel.

### 1. Place the user in control

=> The user should feel that he or she controls the software, not the software controlling the user.

### Guidelines

1. Provide undo, redo, cancel, and back options.
2. Allow flexible navigation.
3. Avoid forcing unnecessary actions.
4. Provide shortcuts for expert users.
5. Give meaningful feedback after user actions.

### Example

=> In an online form, users should be able to edit entered data before final submission.

### 2. Reduce the user's memory load

=> The interface should reduce the amount of information the user must remember.

### Guidelines

1. Use menus, icons, lists, and default values.
2. Show clear labels and instructions.
3. Group related fields together.
4. Use auto-complete and suggestions.
5. Keep screen layout simple.

### Example

=> Instead of asking users to remember product codes, show product names in a drop-down list.

### 3. Make the interface consistent

=> Similar actions and elements should look and behave the same throughout the system.

### Guidelines

1. Use consistent button names.
2. Use same colors and icons for same meaning.
3. Keep navigation style same across pages.
4. Use standard terminology.
5. Display error messages in a consistent format.

### Benefits

1. Reduces user errors.
2. Improves learnability.
3. Increases user satisfaction.
4. Makes software easier to operate.

## Q.4 (b) Explain at least four Software Reliability Metrics. [04]

=> **Software reliability metrics** measure the ability of software to operate without failure for a specified time in a specified environment.

### Reliability metrics

1. **MTTF - Mean Time To Failure**

=> Average time the software operates before a failure occurs.

```text
MTTF = Total operating time / Number of failures
```

2. **MTTR - Mean Time To Repair**

=> Average time required to repair software after a failure.

```text
MTTR = Total repair time / Number of repairs
```

3. **MTBF - Mean Time Between Failures**

=> Average time between two consecutive failures.

```text
MTBF = MTTF + MTTR
```

4. **POFOD - Probability of Failure on Demand**

=> Probability that the system fails when a service request is made.

=> Example: 0.001 means 1 failure in 1000 requests.

5. **ROCOF - Rate of Occurrence of Failure**

=> Frequency of failures in a given time period.

=> Example: 2 failures per 100 hours.

6. **Availability**

=> Percentage of time software is operational and available for use.

```text
Availability = MTTF / (MTTF + MTTR)
```

## Q.4 (a) OR Define Stub and Driver w.r.t. Unit Testing. [03]

=> **Stub** and **Driver** are temporary programs used during unit testing and integration testing.

### Stub

=> A stub is a dummy called module used when the actual lower-level module is not ready.

=> It returns simple fixed output to the calling module.

=> Stubs are commonly used in top-down testing.

### Driver

=> A driver is a dummy calling module used to test a lower-level module.

=> It passes input data and calls the module under test.

=> Drivers are commonly used in bottom-up testing.

### Example

=> If module `A` calls module `B`, and `B` is not ready, a stub for `B` is used. If `B` is ready but `A` is not ready, a driver is written to call `B`.

## Q.4 (c) OR What is McCabe's Cyclomatic Complexity? Explain various steps to find Cyclomatic Complexity using flow graph. [07]

=> **McCabe's Cyclomatic Complexity** is a software metric used to measure the logical complexity of a program.

=> It gives the number of linearly independent paths in a program's control flow graph.

=> It is useful in basis path testing because it gives the minimum number of test cases required to cover independent paths.

### Formula

```text
V(G) = E - N + 2P
```

=> For a single connected program graph, `P = 1`, so:

```text
V(G) = E - N + 2
```

=> Where:

1. `E` = number of edges.
2. `N` = number of nodes.
3. `P` = number of connected components.

### Alternative formula

```text
V(G) = Number of predicate nodes + 1
```

### Steps

1. Read the program or algorithm carefully.
2. Draw a flow graph.
3. Represent statements or blocks as nodes.
4. Represent control flow as edges.
5. Count nodes `N`.
6. Count edges `E`.
7. Apply formula `V(G) = E - N + 2`.
8. Identify independent paths.
9. Prepare at least `V(G)` test cases.

### Example

```text
if (marks >= 40)
    result = "Pass";
else
    result = "Fail";
```

=> There is one decision node.

```text
V(G) = Predicate nodes + 1
V(G) = 1 + 1 = 2
```

=> Minimum two test cases are needed:

1. Marks greater than or equal to 40.
2. Marks less than 40.

### Importance

1. Measures program complexity.
2. Helps design test cases.
3. Identifies risky modules.
4. Encourages simpler code.

## Q.5 (c) Explain any Two Black Box Testing Methods with suitable example. [07]

=> **Black box testing** tests software functionality without knowing internal code structure.

=> Tester focuses on inputs, outputs, and requirements.

### 1. Equivalence Partitioning

=> Equivalence Partitioning divides input data into valid and invalid groups called equivalence classes.

=> One test case from each class is selected because values in the same class are expected to behave similarly.

### Example

=> Suppose age must be between 18 and 60.

| Class | Input | Expected result |
|---|---|---|
| Invalid low | 15 | Reject |
| Valid | 30 | Accept |
| Invalid high | 70 | Reject |

### Advantages

1. Reduces number of test cases.
2. Covers valid and invalid inputs.
3. Easy to apply.

### 2. Boundary Value Analysis

=> Boundary Value Analysis tests values at the boundaries of input ranges because errors often occur at boundary points.

### Example

=> For age range 18 to 60, test values:

```text
17, 18, 19, 59, 60, 61
```

| Input | Expected result |
|---|---|
| 17 | Reject |
| 18 | Accept |
| 19 | Accept |
| 59 | Accept |
| 60 | Accept |
| 61 | Reject |

### Difference

| Equivalence Partitioning | Boundary Value Analysis |
|---|---|
| Tests one value from each class. | Tests values near range boundaries. |
| Focuses on groups of input. | Focuses on edge values. |

### Conclusion

=> These methods improve test coverage without testing every possible input.

## Q.5 (c) OR Explain COCOMO Model for project estimation. [07]

=> **COCOMO** stands for **Constructive Cost Model**.

=> It is an algorithmic software cost estimation model developed by Barry Boehm.

=> It estimates software effort, development time, cost, and staffing based mainly on size of software in KLOC.

### Project modes in Basic COCOMO

1. **Organic mode**

=> Small and simple projects developed by experienced team in familiar environment.

=> Example: Simple business application.

2. **Semi-detached mode**

=> Medium complexity projects with mixed team experience.

=> Example: Compiler or database system.

3. **Embedded mode**

=> Complex projects with strict hardware, software, and operational constraints.

=> Example: Real-time control system.

### Basic COCOMO formulas

```text
Effort (PM) = a * (KLOC)^b
Development Time = c * (Effort)^d
```

=> Where:

1. `PM` = person-months.
2. `KLOC` = thousand lines of code.
3. `a`, `b`, `c`, `d` = constants based on project mode.

### Basic COCOMO constants

| Mode | a | b | c | d |
|---|---:|---:|---:|---:|
| Organic | 2.4 | 1.05 | 2.5 | 0.38 |
| Semi-detached | 3.0 | 1.12 | 2.5 | 0.35 |
| Embedded | 3.6 | 1.20 | 2.5 | 0.32 |

### Types of COCOMO

1. **Basic COCOMO**

=> Estimates effort using only software size and project mode.

2. **Intermediate COCOMO**

=> Uses cost drivers such as reliability, database size, complexity, tools, and team capability.

3. **Detailed COCOMO**

=> Applies estimation to different phases of software development.

### Advantages

1. Simple and systematic estimation.
2. Useful in early project planning.
3. Helps estimate effort, time, and cost.

### Limitations

1. Depends heavily on accurate size estimation.
2. Less suitable for modern reusable and agile projects without adjustment.
3. Constants may not fit every organization.

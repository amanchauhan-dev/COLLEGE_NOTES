## Q.1 (a) Explain Software Engineering as a Layered Technology. [03]

=> **Software Engineering** is called a **Layered Technology** because it is built using several layers that support systematic development of quality software.

### Layers

```text
Tools
Methods
Process
Quality Focus
```

1. **Quality focus**

=> Quality is the foundation of software engineering. Every activity should aim to produce reliable, maintainable, and usable software.

2. **Process**

=> Process defines the framework of activities such as planning, requirement analysis, design, coding, testing, and maintenance.

3. **Methods**

=> Methods provide technical procedures for building software, such as design methods, testing techniques, and estimation methods.

4. **Tools**

=> Tools provide automated support for process and methods.

=> Example: CASE tools, testing tools, version control tools, and project management tools.

## Q.1 (b) Write a short note on Dynamic Systems Development Method (DSDM) in detail. [04]

=> **Dynamic Systems Development Method (DSDM)** is an agile software development framework used for rapid application development.

=> It focuses on delivering business value quickly while keeping customer involvement throughout the project.

### Features of DSDM

1. **Active user involvement**

=> Users are involved continuously to give feedback and validate requirements.

2. **Iterative and incremental development**

=> Software is developed in repeated cycles and delivered in increments.

3. **Time-boxing**

=> Work is divided into fixed time periods. The team delivers maximum possible value within each time-box.

4. **Prioritized requirements**

=> Requirements are prioritized using MoSCoW:

| Category | Meaning |
|---|---|
| Must have | Essential requirements |
| Should have | Important but not critical |
| Could have | Useful if time permits |
| Won't have now | Not included in current delivery |

5. **Frequent delivery**

=> Working software is delivered regularly for review.

### Advantages

1. Fast development.
2. Strong user involvement.
3. Handles changing requirements.
4. Focuses on business value.

=> DSDM is suitable where requirements may change but delivery time is important.

## Q.1 (c) Explain Function oriented metrics with suitable example. [07]

=> **Function-oriented metrics** measure software size and complexity based on the functionality delivered to the user.

=> The most common function-oriented metric is **Function Point (FP)**.

=> It is useful because it estimates software size from user requirements instead of lines of code.

### Function Point components

| Component | Meaning |
|---|---|
| External Inputs (EI) | Data entering the system |
| External Outputs (EO) | Reports or output screens |
| External Inquiries (EQ) | Input-output query transactions |
| Internal Logical Files (ILF) | Logical data maintained by system |
| External Interface Files (EIF) | External data used by system |

### Steps to calculate Function Point

1. Count the number of EI, EO, EQ, ILF, and EIF.
2. Classify each as simple, average, or complex.
3. Multiply each count by its weight.
4. Add all weighted values to get Unadjusted Function Point (UFP).
5. Calculate Value Adjustment Factor (VAF) using general system characteristics.
6. Calculate final Function Point.

### Formula

```text
FP = UFP * VAF
VAF = 0.65 + (0.01 * TDI)
```

=> `TDI` means Total Degree of Influence.

### Example

=> Consider a small library system:

| Component | Count | Weight | Total |
|---|---:|---:|---:|
| External Inputs | 5 | 4 | 20 |
| External Outputs | 4 | 5 | 20 |
| External Inquiries | 3 | 4 | 12 |
| Internal Logical Files | 2 | 10 | 20 |
| External Interface Files | 1 | 7 | 7 |

```text
UFP = 20 + 20 + 12 + 20 + 7 = 79
Assume TDI = 30
VAF = 0.65 + (0.01 * 30) = 0.95
FP = 79 * 0.95 = 75.05
```

### Uses

1. Estimate project effort.
2. Estimate cost and schedule.
3. Compare productivity.
4. Measure software size independent of programming language.

### Advantages

1. Can be used early from requirements.
2. Independent of technology and language.
3. Useful for business applications.

### Limitations

1. Requires experience to classify complexity.
2. Less suitable for algorithm-heavy systems.

## Q.2 (c) Discuss Incremental process model with its diagram and compare it with Waterfall model. [07]

=> **Incremental Process Model** develops software in small releases called increments.

=> Each increment adds useful functionality and delivers a working version to the customer.

### Diagram

```text
Overall requirements
        |
        v
+----------------+   +----------------+   +----------------+
| Increment 1     |   | Increment 2     |   | Increment 3     |
| Core features   |-->| More features   |-->| Final features  |
+----------------+   +----------------+   +----------------+
        |                    |                    |
        v                    v                    v
   Release 1            Release 2            Release 3
```

### Working

1. Requirements are divided into increments.
2. Important features are selected for first increment.
3. First increment is designed, coded, tested, and delivered.
4. Customer feedback is collected.
5. Next increments add more features.
6. Final product is completed after all increments.

### Example

=> For a hotel system:

1. Increment 1: Room booking.
2. Increment 2: Check-in/check-out.
3. Increment 3: Billing and reports.

### Incremental model vs Waterfall model

| Incremental Model | Waterfall Model |
|---|---|
| Software is delivered in multiple increments. | Software is delivered at the end. |
| Supports changing requirements. | Changes are difficult after a phase is complete. |
| Customer feedback is frequent. | Customer feedback is mostly after final delivery. |
| Risk is reduced through early releases. | Risk is discovered late. |
| Testing is done for every increment. | Testing is mainly after implementation phase. |
| Suitable for modular systems. | Suitable when requirements are stable. |

### Advantages

1. Early working software.
2. Better customer feedback.
3. Easier testing and debugging.
4. Important functions delivered first.

### Limitations

1. Requires good architecture.
2. Integration may become complex.
3. Planning increments requires care.

## Q.2 (c) OR Write a note on CRC Modeling. Draw and discuss CRC for the "Email System User". [07]

=> **CRC Modeling** stands for **Class-Responsibility-Collaborator Modeling**.

=> It is an object-oriented analysis technique used to identify classes, their responsibilities, and their collaborations.

### CRC card structure

```text
+-----------------------------------+
| Class Name                         |
+------------------+----------------+
| Responsibilities | Collaborators  |
+------------------+----------------+
| What class does  | Other classes  |
+------------------+----------------+
```

### Terms

1. **Class**

=> A class represents an object or concept in the system.

2. **Responsibility**

=> Responsibility describes what the class knows or does.

3. **Collaborator**

=> Collaborator is another class that helps fulfill a responsibility.

### CRC for Email System User

```text
+------------------------------------------------------+
| Class: EmailSystemUser                               |
+-----------------------------+------------------------+
| Responsibilities            | Collaborators          |
+-----------------------------+------------------------+
| Login to email account      | AuthenticationService  |
| Compose email               | EmailMessage           |
| Send email                  | MailServer             |
| Receive email               | Inbox                  |
| Read email                  | EmailMessage           |
| Delete email                | Inbox, TrashFolder     |
| Manage contacts             | ContactList            |
| Attach files                | Attachment             |
+-----------------------------+------------------------+
```

### Discussion

=> The EmailSystemUser class represents a person using the email system.

=> It does not perform every operation alone. It collaborates with other classes.

### Collaborator roles

1. **AuthenticationService**

=> Verifies username and password.

2. **EmailMessage**

=> Stores subject, body, sender, receiver, and time.

3. **MailServer**

=> Sends and receives messages.

4. **Inbox**

=> Stores received messages.

5. **TrashFolder**

=> Stores deleted messages.

6. **ContactList**

=> Manages saved email contacts.

7. **Attachment**

=> Handles attached files.

### Benefits of CRC modeling

1. Simple and easy to understand.
2. Helps identify classes early.
3. Improves object-oriented thinking.
4. Shows class responsibilities clearly.
5. Helps discover relationships between classes.

## Q.3 (b) Compare coupling and cohesion. [04]

| Coupling | Cohesion |
|---|---|
| Coupling measures dependency between modules. | Cohesion measures relatedness of elements inside a module. |
| Low coupling is desirable. | High cohesion is desirable. |
| High coupling makes changes difficult. | High cohesion makes modules easy to understand. |
| It affects communication between modules. | It affects internal module quality. |
| Example: Module A directly modifies data of Module B. | Example: Salary module only calculates salary. |

### Importance

1. Low coupling improves maintainability.
2. Low coupling improves reusability.
3. High cohesion improves readability.
4. High cohesion reduces defects.

=> A good design has low coupling and high cohesion.

## Q.3 (c) What are the different testing strategies? Explain any one of it with suitable example. [07]

=> **Testing strategy** is a planned approach used to test software at different levels and from different viewpoints.

### Different testing strategies

1. **Unit testing**
2. **Integration testing**
3. **Validation testing**
4. **System testing**
5. **Acceptance testing**
6. **Regression testing**
7. **Performance testing**
8. **Security testing**

### Unit Testing

=> Unit testing tests the smallest testable part of software, such as a function, class, or module.

=> It is usually performed by developers.

### Objectives

1. Check correctness of individual module.
2. Find errors early.
3. Make debugging easier.
4. Verify logic and boundary conditions.

### Unit testing process

```text
Select module
     |
     v
Prepare test cases
     |
     v
Use driver/stub if required
     |
     v
Execute tests
     |
     v
Fix defects and retest
```

### Example

=> Function:

```text

```

=> Test cases:

| Marks | Expected result |
|---:|---|
| 85 | A |

### Driver and stub

=> If the tested module needs a calling module, a driver is used.

=> If the tested module calls another incomplete module, a stub is used.

### Advantages

1. Defects are found early.
2. Reduces cost of debugging.
3. Helps build reliable modules.

## Q.3 (b) OR Discuss cyclomatic complexity. [04]

=> **Cyclomatic Complexity** is a software metric that measures the logical complexity of a program.

=> It gives the number of independent paths in a control flow graph.

### Formula

```text
V(G) = E - N + 2
```

=> Where:

1. `E` = number of edges.
2. `N` = number of nodes.

### Alternative formula

```text
V(G) = Predicate nodes + 1
```

### Uses

1. Measures code complexity.
2. Helps find minimum number of test cases.
3. Supports basis path testing.
4. Identifies risky modules.

### Example

=> If a program has 2 decision nodes:

```text
V(G) = 2 + 1 = 3
```

=> Minimum 3 independent test paths should be tested.

=> SCM ensures that correct versions of code, documents, test cases, and builds are available.

### Need of SCM

1. Software changes frequently.
2. Many developers work together.
3. Multiple versions and releases exist.

### SCM process

```text
Configuration identification
          |
          v
Version control
          |
          v

          |
          v
Configuration audit
          |
          v
```

## Q.4 (c) OR Explain project scheduling process using Gantt chart. [07]

=> **Project scheduling** is the process of defining project tasks, estimating their duration, assigning resources, and arranging them on a timeline.

=> A **Gantt Chart** is a bar chart that shows project activities against time.

### Scheduling process

1. **Identify tasks**

=> Break the project into small activities.

2. **Estimate duration**

=> Estimate time required for each task.

3. **Identify dependencies**

=> Decide which tasks must finish before other tasks can start.

4. **Assign resources**

=> Assign people, tools, and budget to tasks.

5. **Prepare timeline**

=> Arrange tasks on calendar using Gantt chart.

6. **Track progress**

=> Compare actual progress with planned schedule.

### Gantt chart example

```text
Task                  Week1 Week2 Week3 Week4 Week5 Week6
Requirement Analysis  =====
Design                      =====
Coding                            =========== 
Testing                                      =====
Deployment                                         ===
```

### Explanation

=> Each horizontal bar shows start and finish time of a task.

=> Overlapping bars show parallel work.

=> Delayed tasks can be identified by comparing actual progress with planned bars.

### Advantages

1. Easy to understand.
2. Shows project timeline clearly.
3. Helps track progress.
4. Shows task overlap and duration.
5. Useful for project communication.

### Limitations

1. Dependency handling is limited compared to network diagrams.
2. Large projects may produce complex charts.

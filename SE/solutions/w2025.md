## Q.1 (a) Define Software. List out Software characteristics. [03]

=> **Software** is a collection of computer programs, procedures, data, and related documentation used to perform specific tasks on a computer system.

=> Software is not only code. It also includes user manuals, design documents, test cases, configuration files, and operating procedures.

### Software characteristics

1. **Developed, not manufactured**

=> Software is engineered by analysis, design, coding, and testing. It is not produced like hardware in a factory.

2. **Does not wear out**

=> Software does not physically wear out, but it may become obsolete or fail due to design defects, changing requirements, or environment changes.

3. **Mostly custom-built**

=> Many software systems are developed according to specific user or business requirements.

4. **Complex**

=> Software has many interacting modules, logic paths, data structures, and external interfaces.

5. **Easy to modify, but difficult to maintain correctly**

=> A small change can affect many modules if the design is poor.

6. **Intangible**

=> Software cannot be touched physically. Its quality is judged by behavior, performance, reliability, and usability.

## Q.1 (b) What is Agility? Enlist any four Agility Principles. [04]

=> **Agility** is the ability of a software development team to respond quickly and effectively to changing customer requirements, technology, and business conditions.

=> Agile development focuses on iterative delivery, customer feedback, teamwork, and working software instead of heavy documentation.

### Agility principles

1. **Welcome changing requirements**

=> Agile accepts requirement changes even late in development if they give business value.

2. **Deliver working software frequently**

=> Software is delivered in small increments so that customers can review it early.

3. **Customer collaboration**

=> Customers and developers work together continuously to clarify requirements and priorities.

4. **Individuals and interactions**

=> Agile gives importance to communication, teamwork, and problem solving among people.

5. **Working software is the main measure of progress**

=> Progress is measured by completed and usable functionality.

6. **Continuous improvement**

=> The team regularly reviews its process and improves it in the next iteration.

## Q.1 (c) Explain the process model which normally suits for the development of large-scale software system. [07]

=> For large-scale software systems, the **Spiral Model** is normally suitable because it combines iterative development with systematic risk analysis.

=> Large projects have high cost, long duration, changing requirements, technical uncertainty, and many stakeholders. The Spiral Model handles these issues by developing the system in repeated cycles.

### Spiral model diagram

```text
-------------------------+
| 1. Planning             |
| objectives, resources   |
+-----------+-------------+
            |
            v
+-------------------------+
| 2. Risk analysis         |
| identify and reduce risk |
+-----------+-------------+
            |
            v
+-------------------------+
| 3. Engineering           |
| design, code, test       |
+-----------+-------------+
            |
            v
+-------------------------+
| 4. Customer evaluation   |
| review and feedback      |
+-----------+-------------+
            |
            v
       Next spiral cycle
```

### Phases of Spiral Model

1. **Planning**

=> In this phase, project objectives, alternatives, constraints, schedule, cost, and resources are identified.

=> Example: Decide whether the system will be web-based, cloud-based, or client/server.

2. **Risk analysis**

=> Risks are identified, analyzed, and reduced before moving ahead.

=> Risk may be technical risk, cost risk, schedule risk, requirement risk, or performance risk.

=> Prototypes may be created to check whether risky requirements are feasible.

3. **Engineering**

=> Actual development work is performed. It includes design, coding, integration, and testing of the current increment.

=> Each spiral produces a more complete version of the software.

4. **Customer evaluation**

=> Customer reviews the developed version and gives feedback.

=> Feedback is used for planning the next spiral.

### Why it suits large-scale software

1. **Risk-driven approach**

=> Large systems contain many uncertainties, so early risk handling reduces project failure.

2. **Supports changing requirements**

=> Requirements can be refined in each spiral cycle.

3. **Customer feedback**

=> Regular customer evaluation improves correctness and user satisfaction.

4. **Incremental development**

=> The complete system is divided into manageable parts.

5. **Better control**

=> Cost, schedule, risk, and quality can be reviewed after each cycle.

### Advantages

1. Suitable for large and complex projects.
2. Strong risk management.
3. Allows prototyping.
4. Supports requirement changes.
5. Customer involvement is high.

### Limitations

1. Costly for small projects.
2. Requires risk analysis expertise.
3. Management is more complex.

=> Thus, the Spiral Model is preferred for large-scale software because it gives controlled, risk-aware, and iterative development.

## Q.2 (a) What is a spike solution in XP? [03]

=> In Extreme Programming (XP), a **spike solution** is a small experimental program created to investigate a technical problem or unclear requirement.

=> It is used when the team does not know enough to estimate or implement a user story confidently.

### Purpose of spike solution

1. To check technical feasibility.
2. To understand a difficult requirement.
3. To compare possible design or technology options.
4. To reduce risk before actual development.
5. To improve estimation for a user story.

### Example

=> If a team is unsure whether payment gateway integration will work, it may create a small spike to test only payment API connection before building the full payment module.

=> A spike is normally thrown away after learning is complete.

## Q.2 (b) What are the tasks performed in requirement engineering? [04]

=> **Requirement Engineering** is the process of discovering, analyzing, documenting, and managing user needs for a software system.

### Tasks of requirement engineering

1. **Inception**

=> Basic understanding of the problem, stakeholders, business goals, and project scope is developed.

2. **Elicitation**

=> Requirements are collected from customers and users using interviews, questionnaires, observation, brainstorming, and meetings.

3. **Elaboration**

=> Collected requirements are refined into detailed functions, data, behavior, and constraints.

4. **Negotiation**

=> Conflicting or unrealistic requirements are discussed and prioritized according to cost, time, and business value.

5. **Specification**

=> Requirements are formally documented in Software Requirement Specification (SRS).

6. **Validation**

=> Requirements are checked for correctness, completeness, consistency, and feasibility.

7. **Management**

=> Requirement changes are tracked, controlled, and updated throughout the project.

=> Good requirement engineering reduces misunderstanding between developer and customer.

## Q.2 (c) What is Risk Management? Explain RMMM plan. [07]

=> **Risk Management** is the process of identifying, analyzing, planning, and controlling risks that can negatively affect a software project.

=> A risk is a possible future event that may cause loss in cost, schedule, quality, performance, or customer satisfaction.

### Types of software risks

1. **Project risks**: Budget overrun, schedule delay, staff shortage.
2. **Technical risks**: New technology failure, poor performance, integration problem.
3. **Business risks**: Market change, product not accepted, funding stopped.
4. **Requirement risks**: Ambiguous, incomplete, or changing requirements.

### Risk management activities

1. **Risk identification**

=> Identify possible risks using checklists, past project data, team discussion, and expert opinion.

2. **Risk projection**

=> Estimate probability and impact of each risk.

3. **Risk refinement**

=> Break major risks into smaller causes and consequences.

4. **Risk mitigation, monitoring, and management**

=> Prepare actions to reduce, track, and handle risks.

### RMMM Plan

=> **RMMM** stands for **Risk Mitigation, Monitoring, and Management**.

=> It is a project document that describes how risks will be handled during software development.

### 1. Risk Mitigation

=> Mitigation means taking preventive actions to reduce the probability or impact of a risk.

### Examples

| Risk | Mitigation action |
|---|---|
| Requirement change | Use change control and customer reviews |
| Staff leaving | Keep documentation and backup team members |
| New technology failure | Create prototype or spike solution |
| Schedule delay | Add buffer and track milestones |

### 2. Risk Monitoring

=> Monitoring means observing risk indicators throughout the project.

=> The project manager checks whether the risk is becoming more serious.

### Examples

1. Track schedule slippage every week.
2. Check defect rate during testing.
3. Review team workload.
4. Monitor customer change requests.

### 3. Risk Management

=> Management means executing a contingency plan when the risk becomes a real problem.

=> Example: If a key developer leaves, assign a trained backup developer and revise the schedule.

### Contents of RMMM plan

1. List of risks.
2. Risk category.
3. Probability and impact.
4. Mitigation steps.
5. Monitoring indicators.
6. Contingency plan.
7. Responsible person.

=> RMMM improves project control and reduces the chances of project failure.

## Q.2 (c) OR Discuss Software Project Management and W5HH Principle in brief. [07]

=> **Software Project Management** is the activity of planning, organizing, monitoring, and controlling software project resources to complete the project within time, cost, scope, and quality constraints.

=> It includes estimation, scheduling, staffing, risk management, quality management, communication, and progress tracking.

### Need of software project management

1. Software projects are complex and uncertain.
2. Requirements may change during development.
3. Cost and time must be controlled.
4. Team members must coordinate properly.
5. Quality must be maintained.

### Main activities

1. **Project planning**

=> Define scope, objectives, tasks, resources, and milestones.

2. **Estimation**

=> Estimate effort, cost, time, and people required.

3. **Scheduling**

=> Arrange tasks in proper sequence and assign deadlines.

4. **Risk management**

=> Identify and handle project risks.

5. **Tracking and control**

=> Compare actual progress with planned progress and take corrective action.

6. **Quality management**

=> Ensure reviews, testing, and standards are followed.

### W5HH Principle

=> W5HH is a project planning principle suggested by Barry Boehm. It uses seven questions to prepare a practical project plan.

| Question | Meaning |
|---|---|
| **Why** is the system being developed? | Defines business reason and project value. |
| **What** will be done? | Defines project scope and deliverables. |
| **When** will it be done? | Defines schedule, milestones, and deadlines. |
| **Who** is responsible? | Defines roles and responsibilities. |
| **Where** are they organizationally located? | Defines team structure and communication. |
| **How** will the job be done? | Defines technical and management approach. |
| **How much** resource is needed? | Defines budget, effort, tools, and people. |

### Importance of W5HH

1. Gives clarity before project execution.
2. Helps in realistic planning.
3. Improves communication among stakeholders.
4. Reduces confusion about scope and responsibility.
5. Helps project manager track cost, schedule, and resources.

=> Thus, software project management with W5HH helps complete software projects in a disciplined and controlled way.

## Q.3 (b) Compare Coupling and Cohesion. Explain different types of Coupling and its effects on software modules. [04]

### Coupling vs Cohesion

| Coupling | Cohesion |
|---|---|
| Coupling shows dependency between modules. | Cohesion shows relatedness of tasks inside a module. |
| Low coupling is desirable. | High cohesion is desirable. |
| High coupling makes changes difficult. | High cohesion makes module easier to understand. |
| It affects inter-module communication. | It affects internal module quality. |

=> Good software design should have **low coupling** and **high cohesion**.

### Types of coupling

1. **Content coupling**

=> One module directly uses or modifies internal data or code of another module.

=> It is the worst type because any internal change affects other modules.

2. **Common coupling**

=> Multiple modules share global data.

=> Change in global data can affect many modules.

3. **Control coupling**

=> One module passes control information, such as flags, to control the logic of another module.

=> It reduces independence of modules.

4. **Stamp coupling**

=> Modules pass a complete data structure, but only part of it is used.

=> It creates unnecessary dependency on the full structure.

5. **Data coupling**

=> Modules communicate only by passing required data values.

=> It is the best and most acceptable type of coupling.

### Effects on software modules

1. High coupling makes testing difficult.
2. Maintenance becomes costly.
3. Reusability decreases.
4. A change in one module may cause defects in other modules.
5. Low coupling improves modularity, portability, and reliability.

## Q.3 (c) What is testing? Explain the different levels of testing. [07]

=> **Testing** is the process of executing a software system or component to find defects and verify that it satisfies specified requirements.

=> Testing does not prove that software is defect-free. It increases confidence by finding errors before delivery.

### Objectives of testing

1. Find defects in software.
2. Verify requirements.
3. Validate user expectations.
4. Improve quality and reliability.
5. Reduce risk before deployment.

### Levels of testing

```text
---------------------+
| Acceptance Testing |
+---------------------+
| System Testing      |
+---------------------+
| Integration Testing |
+---------------------+
| Unit Testing        |
+---------------------+
```

### 1. Unit Testing

=> Unit testing checks the smallest testable part of software, such as a function, class, or module.

=> It is usually performed by developers.

### Example

=> Testing a function that calculates total marks or validates login password.

### Advantages

1. Finds defects early.
2. Makes debugging easier.
3. Improves confidence in individual modules.

### 2. Integration Testing

=> Integration testing checks whether combined modules work correctly together.

=> It focuses on interfaces, data flow, and communication between modules.

### Approaches

1. Big bang integration.
2. Top-down integration.
3. Bottom-up integration.
4. Sandwich integration.

### Example

=> Testing whether login module correctly connects with database module.

### 3. System Testing

=> System testing tests the complete integrated software system as a whole.

=> It checks functional and non-functional requirements.

### Includes

1. Functional testing.
2. Performance testing.
3. Security testing.
4. Usability testing.
5. Recovery testing.
6. Stress testing.

### 4. Acceptance Testing

=> Acceptance testing is performed to check whether software is acceptable to the customer or end user.

=> It is usually based on business requirements.

### Types

1. **Alpha testing**: Performed at developer site by internal users or customer representatives.
2. **Beta testing**: Performed by selected real users in real environment.

### Conclusion

=> Testing levels move from small modules to the complete system. This systematic approach helps detect defects early and deliver reliable software.

## Q.3 (b) OR How are the concepts of coupling and software portability related? Provide examples to support your discussion. [04]

=> **Coupling** is the degree of dependency between software modules.

=> **Software portability** is the ability of software to run in different environments with minimum changes.

=> Coupling and portability are related because highly coupled software depends strongly on specific modules, platforms, databases, operating systems, or hardware. Such software becomes difficult to move to another environment.

### Relation between coupling and portability

1. **High coupling reduces portability**

=> If business logic directly depends on a specific database, operating system, or user interface, then changing platform requires many code changes.

2. **Low coupling improves portability**

=> If modules communicate through clear interfaces, the internal implementation can be changed without affecting other parts.

3. **Platform dependency creates coupling**

=> Direct use of platform-specific APIs makes software less portable.

4. **Abstraction improves portability**

=> Interfaces, adapters, configuration files, and layered architecture reduce coupling.

### Examples

| Situation | Effect |
|---|---|
| Code directly uses Windows registry APIs. | Difficult to port to Linux. |
| Application directly writes SQL queries for one DBMS everywhere. | Hard to shift from MySQL to PostgreSQL. |
| Business logic is separated from database layer. | Easier to change database. |
| UI code and processing logic are mixed. | Hard to create mobile or web version. |

### Conclusion

=> Low coupling makes modules independent, so software can be modified, reused, and ported more easily.

## Q.3 (c) OR Explain System Testing. [07]

=> **System Testing** is a level of testing in which the complete and integrated software system is tested as a whole.

=> It checks whether the system satisfies functional and non-functional requirements mentioned in the SRS.

=> System testing is usually performed after integration testing and before acceptance testing.

### Need of system testing

1. To verify complete system behavior.
2. To check end-to-end business flows.
3. To detect defects caused by interaction between modules.
4. To validate performance, security, usability, and recovery.
5. To ensure software is ready for customer acceptance.

### System testing process

```text
SRS and design documents
          |
          v
Prepare system test plan
          |
          v
Create test cases and test data
          |
          v
Execute complete system tests
          |
          v
Record defects and retest
          |
          v
Prepare system test report
```

### Types of system testing

1. **Functional testing**

=> Checks whether all required functions work correctly.

2. **Performance testing**

=> Checks response time, speed, throughput, and resource usage.

3. **Stress testing**

=> Tests system behavior under extreme load.

4. **Security testing**

=> Checks whether unauthorized access, data leakage, and attacks are prevented.

5. **Recovery testing**

=> Checks whether system recovers after crash, power failure, or network failure.

6. **Usability testing**

=> Checks whether the system is easy to learn and use.

7. **Compatibility testing**

=> Checks whether software works on different browsers, devices, operating systems, or hardware.

### Example

=> In an online shopping system, system testing checks registration, login, product search, cart, payment, order confirmation, email notification, security, and performance together.

### Conclusion

=> System testing gives confidence that the complete software works correctly in the expected environment.

## Q.4 (c) Write short notes on Reverse Engineering and Forward Engineering. [07]

### Reverse Engineering

=> **Reverse Engineering** is the process of analyzing an existing software system to identify its components, design, architecture, data, and behavior.

=> It works backward from implementation to design or requirement understanding.

### Purpose

1. Understand legacy software.
2. Recover lost documentation.
3. Identify system architecture.
4. Support maintenance and reengineering.
5. Find reusable components.

### Activities

1. Source code analysis.
2. Data structure analysis.
3. Control flow analysis.
4. User interface analysis.
5. Documentation recovery.

### Example

=> If an old payroll system has no design document, reverse engineering can study source code and database tables to create design diagrams.

### Advantages

1. Helps maintain old systems.
2. Reduces dependency on original developers.
3. Improves understanding before modification.

### Forward Engineering

=> **Forward Engineering** is the process of developing software from requirements and design toward implementation.

=> It moves in the normal direction: requirement analysis, design, coding, testing, and deployment.

### Purpose

1. Build a new system.
2. Convert recovered design into improved implementation.
3. Modernize legacy software.
4. Add new features using proper engineering process.

### Activities

1. Requirement specification.
2. Architecture and detailed design.
3. Coding.
4. Testing.
5. Deployment.

### Difference

| Reverse Engineering | Forward Engineering |
|---|---|
| Moves from code to design understanding. | Moves from design to code implementation. |
| Used mainly for existing systems. | Used for new or improved systems. |
| Does not necessarily change software. | Produces working software. |
| Helps recover information. | Helps construct or reconstruct system. |

=> In reengineering, reverse engineering is often performed first to understand the old system, and forward engineering is then used to build the improved system.

## Q.5 (b) What is Cyclomatic complexity? Define Steps to find Cyclomatic complexity using flow graph. [04]

=> **Cyclomatic Complexity** is a software metric used to measure the logical complexity of a program.

=> It represents the number of independent paths in the control flow graph of a program.

=> It helps estimate minimum number of test cases required for basis path testing.

### Formula

```text
V(G) = E - N + 2
```

=> Where:

1. `V(G)` = Cyclomatic complexity.
2. `E` = Number of edges in flow graph.
3. `N` = Number of nodes in flow graph.

### Alternative formula

```text
V(G) = P + 1
```

=> Where `P` is the number of predicate or decision nodes.

### Steps to find cyclomatic complexity

1. Draw the control flow graph from program logic.
2. Represent statements or blocks as nodes.
3. Represent control flow between statements as edges.
4. Count number of edges `E`.
5. Count number of nodes `N`.
6. Apply formula `V(G) = E - N + 2`.
7. The result gives number of independent paths and minimum test cases.

### Small example

```text
if condition:
    statement 1
else:
    statement 2
```

=> There is one decision node.

```text
V(G) = P + 1 = 1 + 1 = 2
```

=> So minimum 2 independent test paths are required.

## Q.5 (c) Explain 7 C's of DevOps Lifecycle. [07]

=> DevOps is a software development approach that combines development and operations teams to deliver software faster, reliably, and continuously.

=> The **7 C's of DevOps lifecycle** describe important continuous activities used for business agility.

### 7 C's of DevOps lifecycle

```text
Collaborate -> Continuous Integration -> Continuous Testing
     -> Continuous Delivery -> Continuous Deployment
     -> Continuous Monitoring -> Continuous Feedback
```

### 1. Collaboration

=> Development, testing, operations, and business teams work together with shared responsibility.

=> It reduces communication gaps and improves delivery speed.

### 2. Continuous Integration

=> Developers frequently merge code into a shared repository.

=> Automated build and basic tests run after every change.

=> It detects integration defects early.

### 3. Continuous Testing

=> Automated tests are executed continuously during development and deployment pipeline.

=> It includes unit tests, integration tests, regression tests, security tests, and performance tests.

### 4. Continuous Delivery

=> Software is always kept ready for release after successful build and testing.

=> Deployment to production may still require manual approval.

### 5. Continuous Deployment

=> Approved changes are automatically deployed to production without manual release steps.

=> It helps deliver features quickly.

### 6. Continuous Monitoring

=> Application, infrastructure, logs, performance, errors, and user behavior are continuously monitored.

=> Monitoring helps detect production problems quickly.

### 7. Continuous Feedback

=> Feedback from users, monitoring tools, testers, and business stakeholders is collected and used to improve the product.

=> It helps teams correct issues and plan future improvements.

### Benefits

1. Faster software delivery.
2. Better product quality.
3. Early defect detection.
4. Improved team collaboration.
5. Quick response to production issues.
6. Higher customer satisfaction.

## Q.5 (a) OR What is software process improvement? [03]

=> **Software Process Improvement (SPI)** is a systematic approach to analyze, evaluate, and improve the software development process.

=> Its goal is to improve quality, productivity, predictability, cost control, and customer satisfaction.

### Need of SPI

1. Reduce defects.
2. Improve development speed.
3. Reduce rework and cost.
4. Make project outcomes more predictable.
5. Improve customer satisfaction.

### SPI activities

1. Study current process.
2. Identify weaknesses.
3. Define improvement goals.
4. Apply improved practices, standards, or tools.
5. Measure results and continue improvement.

=> Models such as CMMI, ISO 9000, and Six Sigma can support process improvement.

## Q.5 (b) OR List out any eight Test Strategies for WebApps. [04]

=> Web application testing checks whether a web application works correctly, securely, and efficiently across different browsers, devices, and network conditions.

### Test strategies for WebApps

1. **Content testing**

=> Checks correctness, spelling, grammar, completeness, and consistency of website content.

2. **Interface testing**

=> Checks links, navigation, forms, buttons, APIs, and communication between components.

3. **Navigation testing**

=> Ensures users can move through pages and menus correctly.

4. **Functionality testing**

=> Checks login, search, registration, payment, upload, and other functions.

5. **Compatibility testing**

=> Checks working on different browsers, operating systems, devices, and screen sizes.

6. **Performance testing**

=> Checks response time, loading speed, throughput, and server behavior under load.

7. **Security testing**

=> Checks authentication, authorization, data protection, SQL injection, XSS, and session security.

8. **Usability testing**

=> Checks ease of use, readability, layout, accessibility, and user satisfaction.

9. **Database testing**

=> Checks data storage, retrieval, update, integrity, and transaction correctness.

10. **Configuration testing**

=> Checks application behavior under different server, network, browser, and client configurations.

## Q.5 (c) OR Explain DevOps Principles. [07]

=> **DevOps** is a culture and practice that integrates software development and IT operations to deliver high-quality software quickly and reliably.

=> DevOps principles guide teams to automate work, collaborate better, and continuously improve software delivery.

### DevOps principles

1. **Collaboration and shared responsibility**

=> Development, testing, operations, and business teams work together instead of working in separate silos.

=> Everyone shares responsibility for quality, delivery, and production stability.

2. **Automation**

=> Repeated tasks such as build, test, deployment, configuration, and monitoring are automated.

=> Automation reduces human error and saves time.

3. **Continuous Integration**

=> Code changes are integrated frequently into a common repository.

=> Automated builds and tests help detect defects early.

4. **Continuous Delivery and Deployment**

=> Software is kept ready for release at any time.

=> Deployment pipelines help release faster with less risk.

5. **Continuous Testing**

=> Testing is performed throughout the lifecycle, not only at the end.

=> Automated testing improves quality and confidence.

6. **Continuous Monitoring**

=> Applications and infrastructure are continuously monitored for performance, availability, errors, and security issues.

=> Monitoring helps teams respond quickly to production problems.

7. **Feedback and continuous improvement**

=> Feedback from users, logs, metrics, and incidents is used to improve product and process.

=> Teams regularly learn from failures and improve practices.

8. **Infrastructure as Code**

=> Infrastructure is managed using code or scripts.

=> It makes environments repeatable, version-controlled, and easier to maintain.

9. **Security integration**

=> Security checks are included early in the pipeline. This is often called DevSecOps.

### Benefits of DevOps principles

1. Faster delivery.
2. Better software quality.
3. Fewer deployment failures.
4. Better team communication.
5. Faster recovery from issues.
6. Higher customer satisfaction.

=> DevOps principles help organizations deliver reliable software continuously with strong collaboration between development and operations.

## Q.1 (a) Identify the definite stages through which a software product undergoes during its lifetime. [03]

=> The definite stages through which a software product passes during its lifetime are called the **Software Development Life Cycle (SDLC)**.

### Stages

1. **Requirement analysis**

=> Understand user needs and prepare SRS.

2. **Design**

=> Prepare architecture, database design, interface design, and module design.

3. **Coding**

=> Convert design into executable programs.

4. **Testing**

=> Find defects and verify that software satisfies requirements.

5. **Deployment**

=> Install and deliver software to users.

6. **Maintenance**

=> Modify software after delivery for correction, improvement, adaptation, or enhancement.

## Q.1 (b) Discuss merits and demerits of spiral model. [04]

=> **Spiral Model** is a risk-driven software process model that combines iterative development, prototyping, and waterfall-style planning.

### Merits

1. **Strong risk management**

=> Risks are identified and reduced in every spiral cycle.

2. **Suitable for large projects**

=> It handles complexity, uncertainty, and changing requirements.

3. **Customer feedback**

=> Customer evaluates each cycle and gives feedback.

4. **Supports prototyping**

=> Prototypes can be created to check risky requirements.

5. **Flexible**

=> Requirements can be refined in later cycles.

### Demerits

1. Costly for small projects.
2. Requires expert risk analysis.
3. Management is complex.
4. Time and cost estimation may be difficult.
5. Too much customer involvement may delay decisions.

## Q.1 (c) Explain prototype model in detail. [07]

=> **Prototype Model** is a software process model in which a working sample of the system is built to understand and refine user requirements.

=> It is useful when requirements are unclear or users cannot explain exactly what they need.

### Diagram

```text
Requirement gathering
        |
        v
Quick design
        |
        v
Build prototype
        |
        v
Customer evaluation
        |
        v
Refine requirements
        |
        v
Final system development
```

### Working

1. **Requirement gathering**

=> Basic requirements are collected from users.

2. **Quick design**

=> A simple design is prepared, mainly for input screens, output screens, and user interaction.

3. **Prototype construction**

=> A quick working model is developed.

4. **Customer evaluation**

=> Customer uses the prototype and gives feedback.

5. **Refinement**

=> Prototype is modified according to feedback.

6. **Engineering final product**

=> After requirements become clear, final software is designed, coded, tested, and delivered.

### Types

1. **Throwaway prototype**

=> Used only for learning requirements and discarded later.

2. **Evolutionary prototype**

=> Prototype is gradually improved into the final system.

### Advantages

1. Helps clarify unclear requirements.
2. Improves customer involvement.
3. Reduces requirement misunderstanding.
4. Useful for UI-heavy systems.
5. Early feedback improves final product.

### Disadvantages

1. Customer may think prototype is final product.
2. Poor prototype design may enter final system.
3. Can increase cost if too many changes are requested.
4. Documentation may be ignored.

=> Prototype model is best when requirements are incomplete, new, or difficult to visualize.

## Q.2 (b) Discuss the differences among Reactive and Proactive Risks. [04]

| Reactive Risk Approach | Proactive Risk Approach |
|---|---|
| Action is taken after the risk becomes a problem. | Risks are identified and planned before they occur. |
| Mainly handles crisis. | Mainly prevents or reduces crisis. |
| Usually causes delay and extra cost. | Helps control cost and schedule. |
| No strong early risk planning. | Includes risk identification, analysis, mitigation, and monitoring. |

=> Proactive risk management is better because it reduces uncertainty before it harms the project.

## Q.2 (c) Explain Extreme Programming (XP) in detail. [07]

=> **Extreme Programming (XP)** is an agile software development method suitable for projects with changing requirements.

=> XP focuses on customer satisfaction, simple design, frequent releases, continuous testing, and close team communication.

### XP process

```text
User stories -> Release planning -> Iteration planning
      -> Design -> Coding -> Testing -> Small release
      -> Customer feedback
```

### XP values

1. Communication.
2. Simplicity.
3. Feedback.
4. Courage.
5. Respect.

### XP practices

1. **User stories**

=> Requirements are written as short stories from the user's point of view.

2. **Planning game**

=> Customer and developers decide priority, cost, and release plan.

3. **Small releases**

=> Working software is released frequently.

4. **Simple design**

=> Design is kept as simple as possible for current requirements.

5. **Pair programming**

=> Two programmers work together on the same code.

6. **Test-driven development**

=> Tests are written before code. Code is accepted when tests pass.

7. **Continuous integration**

=> Code is integrated and tested frequently.

8. **Refactoring**

=> Code structure is improved without changing behavior.

9. **Collective ownership**

=> Any developer can improve any part of the code.

### Advantages

1. Handles requirement changes.
2. Improves quality through continuous testing.
3. Gives early working software.
4. Improves communication.
5. Reduces integration defects.

### Limitations

1. Requires active customer involvement.
2. Difficult for large distributed teams.
3. Needs disciplined developers.
4. Less emphasis on formal documentation.

## Q.2 (c) OR Explain Adaptive software development (ASD) detail. [07]

=> **Adaptive Software Development (ASD)** is an agile process model used for complex and changing software projects.

=> It accepts that requirements may be uncertain and encourages learning through iterative development.

### ASD lifecycle

```text
Speculate -> Collaborate -> Learn
     ^                         |
     |_________________________|
```

### 1. Speculate

=> In this phase, project mission, constraints, basic requirements, and iteration plan are defined.

=> It is called speculate because planning is flexible and expected to change.

### 2. Collaborate

=> Team members, customers, and stakeholders work together to build software features.

=> Collaboration is important because complex systems require shared knowledge.

### 3. Learn

=> The team reviews results, customer feedback, defects, and technical issues.

=> Learning is used to improve the next cycle.

### Characteristics of ASD

1. Mission-focused development.
2. Feature-based planning.
3. Iterative cycles.
4. Strong collaboration.
5. Continuous learning.
6. Tolerance for change.

### Advantages

1. Suitable for uncertain requirements.
2. Encourages innovation and learning.
3. Improves customer involvement.
4. Supports rapid change.

### Disadvantages

1. Requires experienced team.
2. Less suitable for fixed-scope projects.
3. Project control may be difficult if feedback is weak.

=> ASD is useful when the software environment is dynamic and exact requirements cannot be predicted early.

## Q.3 (c) Compute the function points for the following data set: Inputs = 8, Outputs = 12, Inquiries = 4, Logical files = 41, Interfaces = 1 and sum Fi = 41. Assume that all the complexity adjustment values are average. [07]

=> **Function Point (FP)** measures software functionality from the user's point of view.

### Average weights

| Component | Count | Average weight | Value |
|---|---:|---:|---:|
| External Inputs (EI) | 8 | 4 | 32 |
| External Outputs (EO) | 12 | 5 | 60 |
| External Inquiries (EQ) | 4 | 4 | 16 |
| Internal Logical Files (ILF) | 41 | 10 | 410 |
| External Interface Files (EIF) | 1 | 7 | 7 |

### Step 1: Calculate Unadjusted Function Point

```text
UFP = 32 + 60 + 16 + 410 + 7
UFP = 525
```

### Step 2: Calculate Value Adjustment Factor

```text
VAF = 0.65 + (0.01 * sum Fi)
VAF = 0.65 + (0.01 * 41)
VAF = 0.65 + 0.41
VAF = 1.06
```

### Step 3: Calculate Function Point

```text
FP = UFP * VAF
FP = 525 * 1.06
FP = 556.5
```

=> Therefore, the function point value is **556.5**, approximately **557 FP**.

## Q.3 (c) OR Describe difference between Risk components and Risk drivers. [07]

=> **Risk components** are the project areas that may be affected when a risk occurs.

=> **Risk drivers** are the factors or causes that increase the probability or impact of risk.

### Risk components

1. **Performance risk**

=> Risk that software will not meet performance or functional requirements.

2. **Cost risk**

=> Risk that project cost will exceed budget.

3. **Support risk**

=> Risk that software will be difficult to maintain, correct, or support.

4. **Schedule risk**

=> Risk that project will not finish on time.

### Risk drivers

=> Risk drivers influence risk components. They are used to judge how serious each risk is.

### Common risk drivers

1. Product size.
2. Business impact.
3. Customer characteristics.
4. Process definition.
5. Development environment.
6. Technology to be built.
7. Staff size and experience.

### Difference

| Risk Components | Risk Drivers |
|---|---|
| Areas affected by risk. | Causes or factors that create risk. |
| Show what may be damaged. | Show why risk may occur. |
| Example: cost, schedule, performance, support. | Example: inexperienced staff, new technology, unclear requirements. |
| Used to classify impact. | Used to estimate probability and severity. |

### Example

=> If the team uses a new database technology, the **risk driver** is new technology. It may affect **performance risk**, **schedule risk**, and **cost risk**.

## Q.4 (c) Explain coding standard in detail. [07]

=> **Coding standards** are rules and guidelines followed while writing source code.

=> They make code readable, consistent, maintainable, and less error-prone.

### Need of coding standards

1. Improve readability.
2. Reduce programming errors.
3. Make maintenance easier.
4. Support team development.
5. Improve code review quality.
6. Make code reusable and understandable.

### Important coding standards

1. **Naming conventions**

=> Use meaningful names for variables, functions, classes, and files.

=> Example: `calculateSalary()` is better than `cs()`.

2. **Indentation and formatting**

=> Use consistent spacing and indentation to show program structure clearly.

3. **Commenting**

=> Add useful comments for complex logic, assumptions, and important decisions.

4. **Modularity**

=> Divide code into small functions or modules with single responsibility.

5. **Error handling**

=> Handle invalid input, exceptions, and failure cases properly.

6. **Avoid duplicate code**

=> Reuse functions and components instead of copying logic.

7. **Use constants**

=> Avoid magic numbers. Use named constants.

8. **Security practices**

=> Validate input, avoid hardcoded passwords, and protect sensitive data.

9. **Documentation**

=> Maintain code documentation and API documentation where required.

10. **Testing support**

=> Write code in a way that is easy to test.

### Benefits

1. Consistent code style.
2. Easier debugging.
3. Faster onboarding of new developers.
4. Better maintainability.
5. Higher software quality.

## Q.4 (c) OR Explain Web design Pyramid. [07]

=> **Web Design Pyramid** represents important layers used to design a good web application.

=> It helps create web applications that are useful, usable, reliable, and maintainable.

### Web design pyramid

```text
        Aesthetics
      User Interface
   Navigation Design
  Component Design
 Architectural Design
    Data Design
```

### 1. Data design

=> Defines data objects, database structure, relationships, and data flow.

=> Example: Customer, product, order, payment tables in an e-commerce website.

### 2. Architectural design

=> Defines overall structure of web application.

=> Example: Client-server architecture, MVC, layered architecture.

### 3. Component design

=> Defines internal logic of web components such as login, search, cart, payment, and report generation.

### 4. Navigation design

=> Defines how users move between pages and functions.

=> Good navigation should be simple, consistent, and easy to understand.

### 5. User interface design

=> Defines screens, forms, buttons, menus, colors, layout, and interaction.

=> UI should be usable and accessible.

### 6. Aesthetic design

=> Defines visual appearance such as fonts, spacing, images, color balance, and overall look.

=> It should support readability and user experience.

### Importance

1. Organizes web design decisions.
2. Improves usability.
3. Helps maintain consistency.
4. Supports scalable web application design.
5. Reduces design errors.

## Q.5 (b) Explain Black Box Testing. [04]

=> **Black Box Testing** is a testing technique in which the tester checks software functionality without knowing internal code or structure.

=> It focuses on inputs, outputs, and requirement specifications.

### Features

1. Tester does not need programming knowledge.
2. Tests are based on SRS.
3. Used for functional testing.
4. Finds missing functions, interface errors, and behavior errors.

### Techniques

1. Equivalence partitioning.
2. Boundary value analysis.
3. Decision table testing.
4. State transition testing.
5. Cause-effect graphing.

### Example

=> For login, black box testing checks valid username/password, invalid password, blank fields, and locked account behavior.

### Advantages

1. User-focused testing.
2. Useful for validation.
3. Can be done by independent testers.

### Limitations

1. Cannot check internal logic.
2. Some code paths may remain untested.

## Q.5 (c) Explain DevOps Lifecycle in detail. [07]

=> **DevOps lifecycle** describes continuous activities followed to develop, deliver, operate, and improve software.

### Lifecycle

```text
Plan -> Develop -> Build -> Test -> Release -> Deploy -> Operate -> Monitor
             ^_______________________________________________|
                           Feedback
```

### Phases

1. **Plan**

=> Define requirements, user stories, priorities, schedule, and release goals.

2. **Develop**

=> Developers write code and use version control systems like Git.

3. **Build**

=> Source code is compiled and packaged automatically using build tools.

4. **Test**

=> Automated tests verify functionality, performance, security, and regression issues.

5. **Release**

=> Tested build is prepared for deployment.

6. **Deploy**

=> Application is deployed to staging or production environment.

7. **Operate**

=> Operations team manages application infrastructure and availability.

8. **Monitor**

=> Logs, metrics, errors, uptime, and user behavior are continuously monitored.

9. **Feedback**

=> Feedback is used to improve the next development cycle.

### Benefits

1. Faster delivery.
2. Better quality.
3. Improved collaboration.
4. Early defect detection.
5. Better production stability.
6. Faster recovery from failures.

## Q.5 (a) OR What is Cyclomatic Complexity? [03]

=> **Cyclomatic Complexity** is a software metric that measures the logical complexity of a program.

=> It gives the number of independent paths in a control flow graph.

### Formula

```text
V(G) = E - N + 2
```

=> Where `E` is number of edges and `N` is number of nodes.

### Use

1. Measures code complexity.
2. Helps identify risky modules.
3. Gives minimum number of test cases for basis path testing.

## Q.5 (c) OR Explain Formal Technical Reviews. [07]

=> **Formal Technical Review (FTR)** is a structured review process used to find defects in software work products.

=> Work products may include SRS, design document, code, test plan, user manual, or database design.

### Objectives

1. Find defects early.
2. Verify correctness and completeness.
3. Ensure standards are followed.
4. Improve quality.
5. Reduce testing and maintenance cost.

### Participants

1. **Review leader**

=> Plans and controls the review meeting.

2. **Author**

=> Person who created the work product.

3. **Reviewers**

=> Technical people who inspect the work product.

4. **Recorder**

=> Notes defects, decisions, and action items.

### FTR process

```text
Planning -> Preparation -> Review meeting -> Defect recording
        -> Rework -> Follow-up
```

### Steps

1. Review leader schedules meeting.
2. Author distributes review material.
3. Reviewers study material individually.
4. Meeting is conducted with focused discussion.
5. Defects are recorded, not debated personally.
6. Author corrects defects.
7. Review leader verifies corrections.

### Benefits

1. Detects defects before testing.
2. Improves team understanding.
3. Ensures compliance with standards.
4. Reduces rework cost.
5. Improves final software quality.

## Q.1 (a) What is Software Engineering? Justify Software is Engineered but not Manufactured. [03]

=> **Software Engineering** is the application of engineering principles, methods, tools, and processes to develop reliable and maintainable software.

=> Software is **engineered, not manufactured** because it is developed through intellectual activities such as analysis, design, coding, testing, and maintenance.

### Justification

1. Software is not produced by machines like hardware.
2. Major cost is in development, not physical production.
3. Copies of software can be made easily at very low cost.
4. Software does not physically wear out.
5. Quality depends on design, logic, and process.

## Q.1 (b) What is Process? Discuss the process framework activities. [04]

=> A **software process** is a set of activities, methods, practices, and transformations used to develop and maintain software.

### Process framework activities

3. **Modeling**

## Q.1 (c) Explain Spiral Process Model and states its advantages and disadvantages. [07]

=> **Spiral Process Model** is a risk-driven software process model that combines iterative development, prototyping, and waterfall-style systematic development.

### Diagram

```text
Planning
   |
   v
Risk Analysis
   |
   v
Engineering
   |
   v
Customer Evaluation
   |
   v
Next Spiral
```

### Phases

1. **Planning**

=> Identify objectives, alternatives, constraints, schedule, cost, and resources.

2. **Risk analysis**

=> Identify and reduce technical, schedule, cost, and requirement risks.

3. **Engineering**

=> Design, code, test, and develop current version.

4. **Customer evaluation**

=> Customer reviews the developed version and gives feedback.

### Advantages

1. Strong risk management.
2. Suitable for large and complex projects.
3. Supports changing requirements.
4. Allows prototyping.
5. Customer feedback is frequent.
6. Early detection of problems.

### Disadvantages

1. Costly for small projects.
2. Requires risk analysis expertise.
3. Management is complex.
4. Time estimation may be difficult.
5. Too many iterations may delay delivery.

## Q.2 (c) Explain Project Scheduling Process. Also Explain Gantt Chart in detail. [07]

=> **Project scheduling** is the process of dividing project work into tasks, estimating time, assigning resources, and arranging tasks on a timeline.

### Project scheduling process

1. **Identify tasks**

=> Break project into small activities using work breakdown structure.

2. **Estimate duration**

=> Estimate time required for each task.

3. **Identify dependencies**

=> Decide which tasks depend on completion of previous tasks.

4. **Assign resources**

=> Assign people, tools, and budget.

5. **Create schedule**

=> Arrange tasks using Gantt chart or network diagram.

6. **Track progress**

=> Compare actual progress with planned progress.

7. **Revise schedule**

=> Update schedule if delays or changes occur.

### Gantt Chart

=> A **Gantt Chart** is a horizontal bar chart that shows project tasks against time.

### Example

```text
Task                  Week1 Week2 Week3 Week4 Week5
Requirement Analysis  =====
Design                      =====
Coding                            =========
Testing                                  =====
Deployment                                    ==
```

### Advantages

1. Easy to understand.
2. Shows task start and end dates.
3. Helps track progress.
4. Shows overlapping tasks.
5. Useful for reporting project status.

### Limitations

1. Becomes complex for very large projects.
2. Dependency tracking is limited compared to PERT/CPM.

## Q.2 (c) OR Explain COCOMO model for cost estimation. [07]

=> **COCOMO** stands for **Constructive Cost Model**.

=> It estimates software effort, development time, cost, and staffing based on software size in KLOC.

### Project modes

1. **Organic mode**

=> Small simple projects with experienced team.

2. **Semi-detached mode**

=> Medium complexity projects with mixed experience.

3. **Embedded mode**

=> Complex projects with strict constraints.

### Formula

```text
Effort = a * (KLOC)^b
Development Time = c * (Effort)^d
```

### Constants

| Mode | a | b | c | d |
|---|---:|---:|---:|---:|
| Organic | 2.4 | 1.05 | 2.5 | 0.38 |
| Semi-detached | 3.0 | 1.12 | 2.5 | 0.35 |
| Embedded | 3.6 | 1.20 | 2.5 | 0.32 |

### Types

1. Basic COCOMO.
2. Intermediate COCOMO.
3. Detailed COCOMO.

### Advantages

1. Systematic estimation.
2. Useful for planning.
3. Estimates effort and schedule.

### Limitations

1. Requires accurate size estimation.
2. Less suitable for projects with heavy reuse unless adjusted.

## Q.3 (c) Enlist and Explain Requirement Engineering Tasks in detail. [07]

### Importance

1. Reduces misunderstanding.
2. Improves software quality.
3. Reduces rework.
4. Helps prepare design and test cases.

## Q.3 (c) OR What is Risk Management? Explain RMMM plan. [07]

2. Risk projection.
3. Risk refinement.
4. Risk mitigation, monitoring, and management.

=> **RMMM** stands for **Risk Mitigation, Monitoring, and Management**.

3. Probability.

5. Mitigation action.

## Q.4 (b) What is BVA? List out guidelines of BVA. [04]

=> **BVA** stands for **Boundary Value Analysis**.

=> It is a black box testing technique that tests input values at boundaries because defects often occur at edge values.

### Example

=> For valid age range 18 to 60, test values are:

```text
17, 18, 19, 59, 60, 61
```

### Guidelines

1. For range `[min, max]`, test `min-1`, `min`, `min+1`, `max-1`, `max`, `max+1`.
2. For number of input values, test minimum, maximum, one less, and one more.
3. Apply BVA to input and output conditions.
4. Test boundaries of arrays, files, loops, and tables.
5. Include both valid and invalid boundary values.

## Q.4 (c) What is Software testing? Compare: Black box testing and White Box testing. [07]

=> **Software testing** is the process of executing software to find defects and verify that it satisfies requirements.

### Objectives

1. Find defects.
2. Verify requirements.
3. Improve quality.
4. Reduce risk before delivery.
5. Validate user expectations.

### Black box vs White box testing

| Black Box Testing | White Box Testing |
|---|---|
| Tests external functionality. | Tests internal code structure. |
| Tester need not know code. | Tester needs code knowledge. |
| Based on SRS. | Based on program logic. |
| Finds missing or incorrect functions. | Finds logic errors and path errors. |
| Techniques: BVA, equivalence partitioning, decision table. | Techniques: basis path, condition, loop testing. |
| Done mostly at higher testing levels. | Done mostly at unit/integration level. |

### Example

=> For login, black box testing checks valid and invalid login inputs. White box testing checks all branches in login code.

### Conclusion

=> Both testing methods are important. Black box validates functionality, while white box verifies internal logic.

## Q.4 (b) OR What is Cyclomatic Complexity? Define steps to find cyclomatic complexity using flow graph. [04]

=> **Cyclomatic Complexity** measures logical complexity of a program.

=> It gives number of independent paths in a control flow graph.

### Formula

```text
V(G) = E - N + 2
```

=> Where `E` is edges and `N` is nodes.

### Steps

1. Draw control flow graph.
2. Represent statements as nodes.
3. Represent control flow as edges.
4. Count edges `E`.
5. Count nodes `N`.
6. Apply `V(G) = E - N + 2`.
7. Prepare at least `V(G)` test cases.

## Q.5 (c) List and explain the challenges in DevOps Implementation. [07]

=> **DevOps** improves collaboration between development and operations, but implementation can be challenging.

### Challenges

1. **Cultural resistance**

=> Teams may resist moving from separate departments to shared responsibility.

2. **Lack of skills**

=> DevOps requires knowledge of automation, CI/CD, cloud, monitoring, and scripting.

3. **Tool integration**

=> Different tools for build, test, deployment, and monitoring may not integrate easily.

4. **Legacy systems**

=> Old applications may not support automation and frequent deployment.

5. **Security concerns**

=> Fast deployment may create risk if security is not included in pipeline.

6. **Poor communication**

=> DevOps fails if development, testing, and operations teams do not communicate.

7. **Lack of automation**

=> Manual build, test, and deployment reduce DevOps benefits.

8. **Monitoring difficulty**

=> Without good monitoring, production issues cannot be detected quickly.

9. **Management support**

=> DevOps requires support for process change, tools, and training.

### Solutions

1. Train teams.
2. Start with small pilot project.
3. Automate gradually.
4. Use common tools and standards.
5. Include security early.
6. Measure performance using metrics.

## Q.5 (c) OR Explain Software Re-Engineering process model. [07]

=> **Software Re-engineering** is the process of analyzing and modifying existing software to improve maintainability, performance, quality, or functionality.

### Re-engineering process model

```text
Inventory Analysis
        |
        v
Document Restructuring
        |
        v
Reverse Engineering
        |
        v
Code Restructuring
        |
        v
Data Restructuring
        |
        v
Forward Engineering
```

### Activities

1. **Inventory analysis**

=> Identify existing applications and decide which systems need reengineering.

2. **Document restructuring**

=> Create, update, or improve documentation.

3. **Reverse engineering**

=> Analyze existing software to understand design, data, and behavior.

4. **Code restructuring**

=> Improve code structure without changing external behavior.

5. **Data restructuring**

=> Improve database design, file structure, and data organization.

6. **Forward engineering**

=> Build improved software using recovered information and new requirements.

### Benefits

1. Improves maintainability.
2. Extends life of legacy software.
3. Reduces maintenance cost.
4. Improves performance and quality.
5. Preserves useful business logic.

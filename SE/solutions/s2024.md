## Q.1 (a) Describe software engineering as a layered technology. [03]

=> **Software Engineering** is called a **layered technology** because it is organized into layers that support disciplined software development.

```text
Tools
Methods
Process
Quality Focus
```

1. **Quality Focus**

=> Foundation layer. Every activity aims to produce quality software.

2. **Process**

=> Defines framework activities such as communication, planning, modeling, construction, and deployment.

3. **Methods**

=> Provide technical ways to perform requirement analysis, design, coding, testing, and maintenance.

4. **Tools**

=> Provide automated support for process and methods.

## Q.1 (c) Discuss spiral model with diagram and compare it with waterfall model. [07]

=> **Spiral Model** is a risk-driven software process model that combines iterative development, prototyping, and systematic planning.

### Spiral model diagram

```text
Planning
   |
   v
Risk Analysis
   |
   v
Engineering
   |
   v
Customer Evaluation
   |
   v
Next Spiral Cycle
```

### Phases

1. **Planning**

=> Define objectives, alternatives, constraints, cost, schedule, and resources.

2. **Risk analysis**

=> Identify and reduce technical, cost, schedule, and requirement risks.

3. **Engineering**

=> Design, code, test, and develop the current version.

4. **Customer evaluation**

=> Customer reviews the version and gives feedback for next cycle.

### Spiral model vs Waterfall model

| Spiral Model | Waterfall Model |
|---|---|
| Iterative and risk-driven. | Linear and sequential. |
| Risk analysis is done in every cycle. | Risk handling is limited. |
| Supports changing requirements. | Changes are difficult after phase completion. |
| Customer feedback is frequent. | Customer feedback is mostly at the end. |
| Suitable for large and complex projects. | Suitable for small projects with stable requirements. |
| Cost is higher due to risk analysis. | Simpler and less costly to manage. |

### Advantages of spiral model

1. Strong risk management.
2. Supports prototyping.
3. Suitable for large projects.
4. Allows customer feedback.
5. Handles changing requirements.

### Disadvantages

1. Requires risk management expertise.
2. Costly for small projects.
3. More complex to manage.

1. **Developed, not manufactured**

=> Software is engineered through analysis, design, coding, and testing.

## Q.2 (b) Explain Gantt chart in detail. [04]

=> A **Gantt Chart** is a project scheduling tool that shows project activities against time.

=> It is represented as a horizontal bar chart.

### Features

1. Tasks are shown vertically.
2. Time is shown horizontally.
3. Each bar shows start date and end date of a task.
4. Overlapping bars show parallel activities.
5. Milestones and progress can be tracked.

### Example

```text
Task                 Week1 Week2 Week3 Week4 Week5
Requirement          =====
Design                     =====
Coding                           =========
Testing                                  =====
Deployment                                    ==
```

### Uses

1. Plan project schedule.
2. Track progress.
3. Identify delays.
4. Assign resources.
5. Communicate project status.

### Limitation

=> For very large projects, Gantt charts may become complex and dependency tracking may be limited.

## Q.3 (c) Write short note on COCOMO model. [07]

=> **COCOMO** stands for **Constructive Cost Model**.

=> It is an algorithmic model developed by Barry Boehm to estimate software effort, cost, schedule, and staffing.

### Project modes

1. **Organic mode**

=> Small and simple projects with experienced team.

2. **Semi-detached mode**

=> Medium complexity projects with mixed experience.

3. **Embedded mode**

=> Complex projects with strict hardware/software constraints.

### Basic COCOMO formulas

```text
Effort (PM) = a * (KLOC)^b
Development Time = c * (Effort)^d
```

### Constants

| Mode | a | b | c | d |
|---|---:|---:|---:|---:|
| Organic | 2.4 | 1.05 | 2.5 | 0.38 |
| Semi-detached | 3.0 | 1.12 | 2.5 | 0.35 |
| Embedded | 3.6 | 1.20 | 2.5 | 0.32 |

### Types

1. **Basic COCOMO**

=> Uses software size and project mode.

2. **Intermediate COCOMO**

=> Uses cost drivers such as reliability, complexity, tools, and team ability.

3. **Detailed COCOMO**

=> Estimates effort for different development phases.

### Advantages

1. Simple and systematic.
2. Useful for early estimation.
3. Helps estimate cost and schedule.

### Limitations

1. Depends on accurate size estimation.
2. Less suitable if KLOC is unknown.
3. Needs calibration for organization.

## Q.3 (b) OR Explain Earned value analysis in project scheduling. [04]

=> **Earned Value Analysis (EVA)** is a project tracking technique used to compare planned work, completed work, and actual cost.

=> It helps determine whether the project is on schedule and within budget.

### Important terms

1. **Planned Value (PV)**

=> Budgeted cost of work scheduled.

2. **Earned Value (EV)**

=> Budgeted cost of work actually completed.

3. **Actual Cost (AC)**

=> Actual cost spent for completed work.

4. **Schedule Variance (SV)**

```text
SV = EV - PV
```

5. **Cost Variance (CV)**

```text
CV = EV - AC
```

### Interpretation

1. `SV > 0` means ahead of schedule.
2. `SV < 0` means behind schedule.
3. `CV > 0` means under budget.
4. `CV < 0` means over budget.

## Q.3 (c) OR What is risk management? Describe RMMM plan. [07]

=> **Risk Management** is the process of identifying, analyzing, planning, and controlling risks in a software project.

=> A risk is a possible future event that may negatively affect cost, schedule, quality, or performance.

### Risk management activities

1. Risk identification.
2. Risk projection.
3. Risk refinement.
4. Risk mitigation, monitoring, and management.

### RMMM Plan

=> **RMMM** stands for **Risk Mitigation, Monitoring, and Management**.

### 1. Risk Mitigation

=> Preventive action taken to reduce risk probability or impact.

=> Example: Use prototype for risky technology.

### 2. Risk Monitoring

=> Continuously observe risk indicators.

=> Example: Track schedule delay, defect rate, staff availability, and requirement changes.

### 3. Risk Management

=> Apply contingency plan when a risk becomes a real problem.

=> Example: If a key developer leaves, assign trained backup and revise schedule.

### RMMM plan contains

1. Risk list.
2. Probability and impact.
3. Mitigation action.
4. Monitoring indicators.
5. Contingency plan.
6. Responsible person.

### Benefits

1. Reduces uncertainty.
2. Improves project control.
3. Reduces cost and schedule failure.
4. Helps prepare backup plans.

## Q.4 (c) Explain details that should be incorporated in SRS. [07]

=> **SRS** stands for **Software Requirement Specification**.

=> It is a formal document that describes what the software will do and the constraints under which it must operate.

### Details in SRS

1. **Introduction**

=> Purpose, scope, definitions, references, and overview.

2. **Overall description**

=> Product perspective, product functions, user characteristics, constraints, assumptions, and dependencies.

3. **Functional requirements**

=> Detailed services and functions the system must provide.

=> Example: User shall login, search product, and place order.

4. **Non-functional requirements**

=> Quality requirements such as performance, security, reliability, usability, and availability.

5. **External interface requirements**

=> User interface, hardware interface, software interface, and communication interface.

6. **Data requirements**

=> Database, data formats, data validation, and data storage rules.

7. **System constraints**

=> Operating system, programming language, legal rules, hardware limits, and standards.

8. **Use cases or scenarios**

=> User interactions with the system.

9. **Acceptance criteria**

=> Conditions used to decide whether software satisfies requirements.

### Importance

1. Base for design and coding.
2. Helps prepare test cases.
3. Reduces misunderstanding.
4. Supports project estimation.

=> In **layered architecture**, software is divided into layers. Each layer provides services to the layer above it and uses services of the layer below it.

### Diagram

```text
Presentation Layer
        |
Business Logic Layer
        |
Data Access Layer
        |
Database Layer
```

### Explanation

1. **Presentation layer**

=> Handles user interface and user input.

2. **Business logic layer**

=> Handles rules and processing.

3. **Data access layer**

=> Handles database operations.

4. **Database layer**

=> Stores application data.

### Advantages

1. Easy to maintain.
2. Supports separation of concerns.
3. Layers can be modified independently.
4. Improves reuse.
5. Useful for web and enterprise applications.

### Disadvantages

1. Too many layers may reduce performance.
2. Poor layer design can increase complexity.

## Q.5 (c) Describe different types of maintenance in software engineering. [07]

=> **Software maintenance** is the process of modifying software after delivery to correct faults, improve performance, adapt to environment changes, or add features.

### Types of maintenance

1. **Corrective maintenance**

=> Fixes defects found after software delivery.

=> Example: Correct wrong tax calculation in billing software.

2. **Adaptive maintenance**

=> Modifies software to work in changed environment.

=> Example: Updating software to support a new operating system or database.

3. **Perfective maintenance**

=> Enhances software functionality, performance, or usability.

=> Example: Adding report export feature or improving screen design.

4. **Preventive maintenance**

=> Improves internal structure to prevent future problems.

=> Example: Code refactoring, security patching, database optimization.

### Maintenance process

```text
Change request -> Impact analysis -> Approval -> Modification
      -> Testing -> Deployment -> Documentation update
```

### Importance

1. Keeps software useful.
2. Fixes defects.
3. Supports new requirements.
4. Improves performance.
5. Extends software life.

## Q.5 (c) OR Describe phases of DevOps lifecycle. [07]

=> **DevOps lifecycle** contains continuous phases used to deliver and operate software quickly and reliably.

### Diagram

```text
Plan -> Develop -> Build -> Test -> Release -> Deploy -> Operate -> Monitor
             ^_______________________________________________|
                              Feedback
```

### Phases

1. **Plan**

=> Decide requirements, user stories, priorities, and release goals.

2. **Develop**

=> Write source code and use version control.

3. **Build**

=> Compile code and create deployable package.

4. **Test**

=> Run automated functional, regression, performance, and security tests.

5. **Release**

=> Prepare tested build for delivery.

6. **Deploy**

=> Deploy software to staging or production environment.

7. **Operate**

=> Manage application and infrastructure in production.

8. **Monitor**

=> Track logs, errors, performance, availability, and user behavior.

9. **Feedback**

=> Use feedback to improve future releases.

### Benefits

1. Faster releases.
2. Better quality.
3. Improved collaboration.
4. Early defect detection.
5. Faster recovery from failures.
